### G1/G2 — regras transversais
- **G1 (título fora do padrão largeTitle):** **não reproduzido** nesta tela — `teams/index.tsx` já usa `<ThemedText variant="largeTitle">Equipes</ThemedText>` + subtítulo "Gerenciamento" exatamente como o protótipo 28 e como o guia de estilo definem para a raiz de uma aba.

### Dúvidas de produto a documentar sem presumir resposta
- **Cota de gênero na aprovação (achado #1):** o front bloqueia "Aprovar equipe" quando a cota de gênero não está satisfeita, mas `approve_team_adapter.py` nunca valida isso — só o `submit` valida. Isso é proposital (ex.: a intenção é que seja impossível a cota ficar insatisfeita numa equipe já `SUBMITTED`, então o checro do front é só defensivo) ou é uma lacuna real de regra de negócio no backend (alguém pode sair de uma equipe depois de submetida e quebrar a cota, e hoje o backend aprovaria mesmo assim)? R: Confirmado como lacuna real — implementar o checro de cota também no `approve_team_adapter.py`, no mesmo padrão do `submit`.
- **Equipes em rascunho visíveis ao monitor (chip "Rascunho", `teams/index.tsx`):** o monitor consegue filtrar e ver equipes que o dono ainda nem submeteu (`STATUS_COPY.DRAFT`: "ainda não há o que aprovar"). É intencional dar essa visibilidade ao monitor, ou o filtro "Rascunho" deveria existir só do lado do aluno? R: Sim, intencional. O monitor pode acompanhar o progresso das inscrições. R: Realmente, o monitor não deveria ver equipes rascunhos.
- **Protótipo para os estados `APPROVED`/`REJECTED` do detalhe, visão do monitor:** as imagens 28–30 só cobrem a listagem e o fluxo de aprovar/rejeitar uma equipe `SUBMITTED`. Não há protótipo mostrando como o monitor vê o detalhe de uma equipe já aprovada ou já rejeitada (o código mostra `TeamStatusBadge`, e para rejeitada, um bloco com o motivo — linha ~312). Não é um bug, mas o comportamento desses dois estados foi implementado sem referência visual — vale confirmar com quem definiu o protótipo se esse layout "genérico" é o esperado ou se falta uma tela específica.
