Não houve execução num dispositivo/emulador real. A leitura cruzada com o backend permitiu **confirmar a causa raiz exata** do erro genérico pré-notado (achado #1 abaixo), algo que não seria possível concluir com certeza só pelo front. Itens marcados como **"a confirmar em dispositivo/após correção"** dependem do achado #1 ser corrigido antes de poderem ser exercitados de ponta a ponta (hoje a tela nunca chega a renderizar conteúdo real para aluno/visitante, só o estado de erro).

| 1 | Toda a tela (`brackets-screen.tsx`) | **Causa raiz confirmada do erro pré-notado.** As três rotas que esta tela consome — `GET /api/bracket/season/{season_id}`, `GET /api/bracket/{bracket_id}` e `GET /api/bracket/{bracket_id}/matches` — exigem papel de **monitor** no backend: todas usam `current_user: User = Depends(require_monitor)` em `web/controllers/bracket_controller.py` (linhas 64, 99, 130, 160, e também nas de escrita). `require_monitor` (`web/dependencies/security_dependencies.py`) rejeita qualquer usuário que não seja `MONITOR`/`ADMIN` com `HTTPException(403, "Você não tem permissão para realizar essa ação")`. ### Observações adicionais (além dos pontos pré-notados)
- A pílula "Atualizado ao vivo" no `subHeader` do mata-mata (`brackets-screen.tsx`) depende de `isLive`, calculado a partir de `scoreByMatchId` (preenchido por `useMatchList`, que é uma chamada separada de `GET` de partidas — essa consulta **não** usa `bracketService`, então não é afetada pelo `require_monitor` do achado #1). Isso significa que, mesmo hoje, o indicador de "ao vivo" poderia em teoria carregar, mas nunca chega a aparecer porque a tela já trava antes, no carregamento dos chaveamentos (`brackets.isError`) — vale confirmar depois da correção se esse indicador realmente aparece e atualiza em tempo real como esperado.
- `app/(tabs)/(brackets)/[modalityId].tsx` (entrada vinda de notificação/link profundo para uma modalidade específica) usa o mesmo componente e sofre o mesmo bloqueio do achado #1 — não há nada de diferente a relatar nessa rota além do que já foi dito para `index.tsx`.
- G2 (`Alert.alert`) não se aplica a este fluxo: é uma tela somente leitura para o aluno/visitante, sem nenhuma ação de confirmação. Busca por `Alert.alert` nos arquivos do fluxo não encontrou ocorrências.
- G4 (picker de "apenas data") não se aplica: não há campo de edição de data nesta tela (a edição de partida é exclusiva do fluxo M6).
- Este mesmo componente (`BracketsScreen`, `KnockoutBracket`, `GroupBracket`, `StandingsTable`) é reaproveitado por M5 (chaveamento visto pelo monitor), mas **M5 não deveria ter o problema do achado #1**, já que o monitor de fato tem o papel exigido por `require_monitor` — esse achado é específico de A3 (aluno/visitante acessando a mesma rota `(tabs)/(brackets)/...`). Os achados #3, #4, #5 e #6 (título, modalidade, legenda de classificação, match card), por serem do mesmo componente visual, **também valem para M5** e não devem ser tratados como bugs distintos na correção — a sessão de M5 deve referenciar este relatório em vez de redescobrir os mesmos pontos.

| 1 | `components/brackets/standings-table.tsx` (`sortStandings`) | A tabela de classificação reordena os times recebidos usando só três critérios: pontos → saldo de gols → gols pró (`sortStandings`), **descartando a ordem em que o backend já envia `group.teams`**. | **Checado no backend** (`business/bracket/_standings.py`, `order_group_standings`, usado por `get_bracket_details_adapter.py` e exposto em `BracketDetailResponse.groups[].teams` via `web/mappers/bracket_model_mapper.py`): o backend já aplica uma classificação de **8 critérios em cascata** (confronto direto → maior número de vitórias → saldo entre os empatados → aproveitamento entre os empatados → menor número de gols sofridos geral → saldo geral → aproveitamento geral → sorteio), equivalente ao critério oficial de desempate de campeonatos de pontos corridos, e já devolve `teams` nessa ordem correta.
