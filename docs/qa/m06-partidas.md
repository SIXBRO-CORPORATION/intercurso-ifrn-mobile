| 1 | `matches/index.tsx` (lista) | **Bug pré-notado confirmado, com causa raiz identificada.** `useMatchList` (`hooks/useMatches.ts`) é um `useInfiniteQuery` cuja `queryKey` inclui `status` e `modalityId` (`queryKeys.matches.list(filters)`). Trocar o `Segmented` (Agendadas/Em andamento/Encerradas) ou o filtro de modalidade muda essa chave, e o React Query trata isso como uma **query nova**: `list.isPending` volta a `true` até a resposta chegar. Como `renderEmpty()` retorna `<LoadingState>` quando `isPending`, e o `FlatList` usa `ListEmptyComponent={renderEmpty}` com `data={matches}` (que vira `[]` enquanto não há dado para a nova chave), a lista inteira some e um spinner de carregamento aparece no lugar — exatamente o "flash"/piscada relatado. Não há `placeholderData: keepPreviousData` (API do `@tanstack/react-query` v5, instalado aqui) configurado na query, que é o mecanismo desenhado para esse exato cenário (manter os dados da aba anterior visíveis, com um indicador de "atualizando em segundo plano", enquanto a nova página carrega). | Confirmado | Alto |
| 2 | `matches/[matchId].tsx` (editar, 35) | **G4 também confirmado aqui, com uma pista concreta de causa raiz.** `EditMatchForm` usa dois `DateField` lado a lado sobre o **mesmo** estado `date`: um `mode="date"` ("Data") e um `mode="time"` ("Hora"). Olhando `date-field.tsx`: o branch `mode="time"` sempre chama `onChange(mergeDateAndTime(value, time))`, preservando a data ao mudar só a hora — correto. Mas o branch `mode="date"` **só** faz o merge quando `showTime` é `true` (ou seja, quando o próprio campo é `mode="datetime"`); quando o campo é `mode="date"` puro — exatamente o caso usado aqui —, tanto no iOS (`onChange(date)`) quanto no Android (`onChange(date)` dentro de `androidStep === 'date'`, ramo `else`) o valor é aplicado **sem mesclar com a hora já escolhida no campo "Hora" vizinho**. Se o picker nativo (`@expo/ui/community/datetime-picker`) devolver um `Date` com a hora zerada/alterada ao invés de preservar a hora do `value` recebido, trocar só a "Data" apaga silenciosamente a "Hora" já selecionada, sem nenhum aviso ao usuário — o formulário mostraria "Hora: 15:30" errado só depois de salvar e recarregar, ou o `handleSave` enviaria um horário incorreto sem o monitor perceber. Não dá para confirmar por leitura de código puro (o componente nativo do picker Android é um módulo Jetpack Compose fora do JS) se isso realmente zera a hora nos dois sistemas — por isso o G4 segue como item de teste em dispositivo —, mas agora há uma linha de código específica (`date-field.tsx`, branch `mode="date"` dos dois `onValueChange`) para olhar primeiro. | A confirmar em dispositivo (iOS e Android separadamente) — causa raiz candidata identificada | Alto |

### Observação adicional (fora dos pontos pré-notados)
- `types/match-list.ts` (`MatchListFilters`) e `services/match.service.ts` (`listMatches`) já suportam `dateFrom`/`dateTo` como parâmetros de busca (`date_from`/`date_to` na query string), mas `matches/index.tsx` nunca os usa — não existe nenhum filtro de data na UI. Não é uma divergência do protótipo (que também não mostra filtro de data), só uma capacidade do back que o front não expõe; registrado para referência caso a Fase 2 de algum outro fluxo precise de filtro por data de partida.
